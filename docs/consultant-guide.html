FileMaker Security Audit workflow

Everything you need to run a best-practice security audit of a client's FileMaker Server and the files it hosts, from opening the repo to handing over the report. This page replaces reading the README, AGENTS.md, the skills and the checklist separately.

Version 0.1 · Rule set and commands as in the fms-security-audit repo · About an hour per server once you have access

Status. Tested end to end on fictitious data, with the XML parser tested on a scrubbed real FileMaker 26 export and the Mac script run on a Mac workstation. Not yet run against a live client server or a real Windows server. If a server returns data in a shape the collector doesn't expect, the affected checks show Not checked. That is safe: the report never guesses.

The audit at a glance

The client gets a dated, point-in-time review that says what passes, what doesn't, and how to fix it. It is built to catch the drift we see after a server is handed over: privileges opened up to get something built, and everyone working on Full Access accounts. Fixing the findings is the client's call and the client's work, unless they hire us to help.

Three inputs feed one report. Everything runs from your own laptop. Nothing is installed on the server and nothing on it changes.

HTTPS from your laptop

Server checklist

FileMaker Admin API and OttoFMS, GET requests only. Version, certificate, encryption, web publishing, backups, schedules, plug-ins, API keys.

server.json · otto.json
Your remote desktop session

OS checklist

One read-only script pasted into PowerShell or Terminal. Ports, firewall, patching, admins, disk encryption, antivirus.

os.json
FileMaker Pro on your laptop

File audit

Save a Copy as XML of each hosted file. Accounts, privilege sets and extended privileges.

files.json
Rules in rules/ decide Pass, Warn, Fail or Not checked → findings.json, report.html, report.pdf

What it does not do

It does not monitor the server over time, read or review logs, test or crack passwords, check password policy, scan or probe the server from outside the network, or do penetration testing. External testing is a separate service with its own authorization. The report says so in plain words.

Ground rules

These come straight from the agent instructions and apply to you as much as to Claude Code or Codex.

Always

  • Type passwords only at the local audit login prompt, in a terminal window of your own.
  • Keep client data inside audits/, which git ignores.
  • Run the OS script exactly as given, inside your normal remote desktop session.
  • Let the rules decide every status. You and the agent write only the executive summary.
  • If a result looks wrong, fix the input (answers.yaml) or raise the rule.

Never

  • Paste a password into Claude or Codex. If one lands there, stop and have the client change it.
  • Install anything on the client's server, or change any setting there.
  • Scan, probe or test the server from outside its network.
  • Commit, attach or paste anything from audits/, including raw XML, into git, an issue or a pull request.
  • Edit findings or the report by hand to work around a failing command.

Install once

git clone https://github.com/datacraftdevelopment/fms-security-audit.git
cd fms-security-audit
python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python -m pytest                 # optional: confirms everything works

For PDF reports, add Playwright. Without it you still get the HTML report, which prints to PDF from any browser.

pip install playwright
python -m playwright install chromium

Install the secret-scanning hook so a credential can never be committed by accident:

pip install pre-commit && pre-commit install

Before each audit, run git pull so you have the current rules.

The workflow

Open the repo folder in Claude Code (claude) or Codex (codex) and ask “What do I do?” The agent follows these nine steps one at a time: it asks, waits for your answer, then moves on. Each step also lists the plain command it runs, so you can do the whole audit by hand. The examples use a client called Example Co with a server at fms.example.com.

Any step can be skipped if its access isn't available. Its checks then show as Not checked. Never stop the whole audit because one source is missing.

  1. Check the prerequisites

    You + agentfms-audit

    The agent asks whether you have each item in What you need and explains any you don't recognise. If Python is missing, it helps you install it and runs pip install -r requirements.txt.

  2. Start the audit folder

    Agentfms-audit

    Give the client name, the server hostname, and whether the server runs Windows or macOS.

    python -m audit new "Example Co" --server fms.example.com
# creates audits/example-co/2026-10-30/ from audits/_template/

    The folder name is the client slug and today's date; add --date YYYY-MM-DD to set another. If an earlier folder exists for the same client, note it: the report will compare against it.

    Produces answers.yaml (client, server and date filled in) and an empty xml/ folder.

  3. Answer the client questions

    Youfms-audit

    The rules need a few judgment calls only you or the client can make. The agent asks them once, in plain words, and saves the answers to answers.yaml.

    FieldWhat to put
    platformwindows or mac
    ottofms_installedtrue or false
    developer_accountsAccounts that genuinely need Full Access: RCC's, the client's IT lead
    data_api_sets, odata_sets, webdirect_setsPrivilege sets that are supposed to have fmrest, fmodata or fmwebdirect. If unsure, leave empty; the report flags them for review
    export_denied_setsSets the client says should not export or print. Empty means FIL-06 shows Not checked
    consultant, firmWho did the audit; the firm appears in the disclaimer
    summaryLeft empty for now; written in step 8

  4. Log in at the local prompt

    You, in your own terminalfms-connect

    Open a separate terminal window, not the agent chat, and run:

    python -m audit login fms.example.com
python -m audit check-connection fms.example.com

    The password prompt doesn't echo, and the credentials go into your OS keychain (macOS Keychain or Windows Credential Manager). Add --otto to login only if OttoFMS uses different credentials. Tell the agent when check-connection prints “Admin API login works.”

    In Claude Code, never run audit login with the ! shell prefix. Its output would land in the conversation.

    If it fails: can you open the Admin Console in a browser from this laptop? If not, it's the network or VPN. A certificate warning is itself a finding (SRV-02); continue with --allow-untrusted-cert only after the client agrees. A wrong password means running login again.

  5. Collect the server settings

    Agentfms-server-auditottofms-audit
    python -m audit collect server fms.example.com --out audits/example-co/2026-10-30/
python -m audit collect otto   fms.example.com --out audits/example-co/2026-10-30/   # only if OttoFMS is installed

    The collector logs in with the keychain credentials, sends only GET requests, and logs out. The HTTP layer refuses anything else, and a test checks that. It reads the server version, hosted files with their encryption and extended privileges, web technology settings, “host password-protected files only”, backup and script schedules with their accounts and last results, plug-ins, certificate details where the API exposes them, and connected clients (used for FIL-08).

    The OttoFMS collector reads the version, licence status, and each API key's label, file, created, last used and expiry dates. It never saves key secrets. If it says OttoFMS did not answer, set ottofms_installed: false.

    Produces server.json, server_raw.json (what the API returned, for troubleshooting) and otto.json.

  6. Run the OS check in your remote desktop session

    Youfms-os-audit
    python -m audit os-script win      # or: mac. Copies the script to your clipboard

    Paste it into an elevated PowerShell (Windows) or Terminal (Mac) on the server, then copy the result block back to your laptop:

    python -m audit os-import --out audits/example-co/2026-10-30/

    Full instructions, what the script reads, and what happens without admin rights are in The OS script.

    Produces os.json.

  7. Export each file's XML

    You or the clientfms-file-audit

    The agent lists the hosted files from server.json so none is missed. For each one, Save a Copy as XML into the audit folder's xml/ subfolder, then:

    python -m audit parse-xml audits/example-co/2026-10-30/

    This reads accounts, privilege sets and extended privileges into files.json, then deletes the XML files, because a Save as XML export can contain encrypted password hashes. Any hosted file without an XML shows Not checked. Details and client-ready instructions are in The XML export.

    Produces files.json.

  8. Build and review the report

    Agent, then youfms-report
    python -m audit evaluate audits/example-co/2026-10-30/      # prints the fail / warn / pass / not checked counts

    The agent shows you the counts and walks you through each Fail. It then drafts the executive summary into summary in answers.yaml: three to five plain sentences on the most serious findings. Edit it as you like, then build:

    python -m audit report audits/example-co/2026-10-30/ --pdf
# add --previous audits/example-co/<earlier-date>/ for a re-audit

    Read the whole report before sending it. The summary is the only part anyone writes; every status, table and count comes from the rules.

    Produces findings.json, report.html and, with Playwright, report.pdf.

  9. Close out

    Youfms-audit
    python -m audit logout fms.example.com

    Deliver the PDF to the client's named contact, move the audit folder to RCC's secure client storage, and ask the client to rotate the credentials they lent. Then work through the close-out checklist.

The OS script

One self-contained script, pasted into a terminal in the remote desktop session you already have. It only reads. It writes no files and installs nothing. No SSH, WinRM or file transfer is needed. The scripts live in scripts/; never modify them to change settings.

Windows server (RDP)

  1. On your laptop: python -m audit os-script win
  2. In the RDP session, right-click Start and open Terminal (Admin), or PowerShell with Run as administrator.
  3. Paste and press Enter.
  4. The result block prints and is copied to the server's clipboard.

Mac server (Screen Sharing)

  1. On your laptop: python -m audit os-script mac
  2. In the Screen Sharing session, open Terminal.
  3. Paste and press Return. Enter the admin password once when sudo asks, or press Ctrl-C to skip the admin-only reads.
  4. The result block prints and is copied to the server's clipboard.

The result looks like this. It carries a checksum, so a block that was cut off while copying is rejected rather than half-read.

----- FMS-AUDIT OS BEGIN v1 -----
H4sIAAAAAAAAA+1YW2/bNhR+z68g9Lwl1t0O0IeiSLEB...
sha256: 9f2c...e41a
----- FMS-AUDIT OS END -----

Back on your laptop, python -m audit os-import --out <folder> reads your clipboard. If the clipboard doesn't sync over remote desktop, select everything from BEGIN to END by hand, or save it to a text file and use --file block.txt (or pipe it with --stdin).

What needs admin rights

Without admin rights the script still runs. What it couldn't read shows as Not checked, with the reason. That's acceptable, but say so in the summary.

Needs adminWindowsMac
NoOS version, patches, firewall profiles and rules, local admins, listening portsOS version, updates, application firewall, admin group, FileVault status
YesBitLocker, Defender settings and exclusions, some process namesProcess names behind each port, pf rules

The only trace left on the server is the pasted text in that terminal's history. Close the window when you're done.

The XML export

For each file the server hosts:

  1. Open the file from the server in FileMaker Pro, signed in with a Full Access account.
  2. Choose File > Save a Copy as XML, with only the accounts and security information selected if your version offers the choice.
  3. Name it after the file, for example Invoices.xml, and save it to audits/<client>/<date>/xml/.

Use Save a Copy as XML, not a Database Design Report. Plain passwords are never in the export, but it can contain encrypted password hashes, so treat the files as sensitive: never open them in the chat, copy them elsewhere or commit them. The parser never reads the hashes, and it deletes the XML once read. Add --keep-xml only to debug the parser.

Instructions you can send the client

If someone at the client is doing the export, send them this. The agent can also print a version with the file names filled in.

For each FileMaker file on the server:

1. Open the file in FileMaker Pro and sign in with a Full Access account.
2. Choose File > Save a Copy as XML. If you are offered a choice of
   what to include, choose only accounts and security information.
3. Name the export after the file, for example Invoices.xml.
4. Send the exports to us by the secure method we agreed, not by email.

The export does not contain any record data or plain-text passwords,
but it does contain encrypted password information, so please delete
your copies once we confirm we have them.

The 27 checks

Each check has a fixed ID, so findings can be compared between audits. Thresholds are defaults set in rules/*.yaml. The “typical fix” is the remediation text the report prints.

Server, from the Admin API and OttoFMS

IDCheckFails or warns whenTypical fix
SRV-01FileMaker Server versionBelow the minimum safe version (default 22.0.4)Update after a verified backup, in a maintenance window
SRV-02SSL certificateDefault Claris certificate, expired, or expiring within 30 daysInstall a trusted certificate for the hostname and renew before expiry
SRV-03Encryption at restAny hosted file not encryptedEncrypt with the FileMaker Developer Utility and host the encrypted copy
SRV-04Host password-protected files onlySetting is offTurn it on in the Admin Console
SRV-05Web technologiesData API, OData, WebDirect, XML or PHP on without a stated needTurn off every web technology the client doesn't use
SRV-06Backup schedulesNo enabled backup schedule, or the last run failedKeep one enabled, check results, test a restore
SRV-07Script schedulesWarns on schedules run by a Full Access account; Not checked when the API doesn't say which accountRun them under a dedicated, least-privilege account
SRV-08Plug-insListed for reviewRemove unused plug-ins, keep the rest current
SRV-09OttoFMSInvalid licence, API keys with no expiry, or expired keys still listedKeep OttoFMS current and give every key an expiry

Reading the report

The report runs in this order: cover, executive summary with the tally, scope and method, server checklist, OS checklist, one section per file, a remediation plan with Fails first, an appendix (every account by file, installed plug-ins), and the disclaimer last. See the sample report for a full example with fictitious data.

FailA real exposure to fix, such as an expired certificate or Guest access to data.
WarnReview it. Often fine with a reason, such as an extra Full Access account.
PassMeets the standard at the time of the audit.
Not checkedThe data wasn't available. The finding says why.

Re-audits and drift

To see what changed since the last audit, point the report at the previous folder:

python -m audit report audits/example-co/2027-04-30/ --previous audits/example-co/2026-10-30/ --pdf

Each Warn and Fail is marked new or unchanged, and a “Fixed since last audit” list shows what was resolved. This only works if the earlier folder still has its findings.json, so keep finished audit folders in RCC storage.

Keeping client data safe

WhatHow it's protected
PasswordsTyped only at the local login prompt and stored in the OS keychain. Never in files, the repo or the AI conversation. If one ends up in a chat, have the client change it.
Client dataLives only under audits/, which git ignores except for the template. Never commit it, attach it to an issue, or paste it into a pull request.
XML exportsCan contain password hashes. Deleted after parsing, and git ignores *.xml outside samples/ and tests/fixtures/. Anything placed in tests/fixtures/ must be scrubbed first.
The serverRead-only by design: the HTTP session blocks every request except GET plus the Admin API login and logout, and a test checks that. The OS scripts only read.
AI processingAccount names and server settings pass through the AI tool you use. Make sure that fits the engagement letter.
CommitsThe pre-commit hook scans for secrets. Don't turn it off.

Troubleshooting

ProblemWhat to do
No stored credentials for <host>Run python -m audit login <host> in your own terminal. The host must match exactly.
Admin API login failed (401)Wrong Admin Console credentials, or the account is locked. Check in a browser at https://<host>/admin-console.
Can't reach the server at allNetwork or VPN. If the Admin Console doesn't open in your browser, the audit tools can't reach it either.
Certificate not trustedThat's a finding (SRV-02). Re-run with --allow-untrusted-cert only if the client agrees.
Many server checks show Not checkedThe server returned fields the collector doesn't recognise yet. Look at server_raw.json in the audit folder and open an issue describing the field names. Never attach the file.
OttoFMS did not answerIt probably isn't installed. Set ottofms_installed: false.
Clipboard doesn't sync over RDPTurn on clipboard redirection in your RDP client, or copy the block by hand, or save it to a file and use os-import --file.
os-import says the checksum doesn't matchThe block was cut off. Copy it again from BEGIN to END.
parse-xml finds no accountsMake sure it was Save a Copy as XML, not a Database Design Report, made with a Full Access account. If it still finds none, the export format may differ; tell the repo maintainers rather than guessing at results.
Client won't share a Full Access loginSend them the export instructions.
A finding looks wrongCheck answers.yaml. If the rule itself is wrong, raise it in the repo. Don't edit the report by hand.
No PDFInstall Playwright (see Install once), or open report.html in a browser and print to PDF.

Command reference

Every command is python -m audit <command>, run from the repo folder.

login <host>Prompts for the Admin Console login and stores it in the keychain. Your own terminal only--otto for separate OttoFMS credentials

logout <host>Deletes the stored credentials for that host

    ├── _template/

  • Thresholds and fix text are in rules/*.yaml. For example, the minimum server version is min_version under SRV-01, and the Full Access limit is max_full_access under FIL-01. Keep the minimum version current with Claris security bulletins.

  • Bump RULESET_VERSION in audit/__init__.py when you change a check, so reports show which standard they used.
  • After a change, run python scripts/build_sample.py to regenerate the sample report, then python -m pytest.

Disclaimer

This tool produces a point-in-time review against the checks listed. It is not continuous monitoring, and a clean report does not guarantee that a system is secure. The client remains responsible for its servers, files and remediation. Every client report ends with this disclaimer, and it must not be removed or shortened.
